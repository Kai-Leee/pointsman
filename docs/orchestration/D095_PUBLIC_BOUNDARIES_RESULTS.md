연구 보관: [마무리 기록](../research/D095_CLOSEOUT.md) · [공개 수치 요약](../research/evidence/d095/summary.json). 아래 `benchmark-runs/` 링크는 보존된 로컬 원본용이며 GitHub에는 포함하지 않았다. 본문의 commit/push 미수행 상태는 실험 종료 당시 기록이다.

최종 수정 조건은 **공개 93/93, 독립 63/63으로 완료**했다. 이전에 실패한 독립 검사 4개도 같은 검사 집합에서 모두 통과했다. 다만 과거 Claude 단독 완료 실행 대비 전체 시간이 12.43%, 캐시 포함 토큰이 68.67%, 참고 환산 비용이 30.81% 증가했다. **완료 품질은 확보했지만 시간·비용 절감 목표는 달성하지 못했다.**

## 이전 독립 검사 4개가 실패한 원인

- **3개:** 응답 모델이 생성·export되지 않아 API 모듈 import에서 중단됐다. `build_models`가 실제 `ModelContext`를 반환하지 않고 두 목록만 반환하므로, 생성기는 inline 모델 등록 함수가 없는 대체 컨텍스트를 사용했다. 클래스 이름은 만들어도 해당 모델은 출력하지 못했다. 실제 컨텍스트를 전달하더라도 늦게 등록된 모델의 dict를 생성기가 합치지 않는 문제가 뒤따랐다. 경로 인코딩과 두 form 테스트는 본 동작에 도달하기 전에 실패했으므로, 세 전송 기능 자체가 잘못됐다는 증거로 분류하지 않았다.
- **1개:** 숫자로 시작하는 속성명 `7value`를 이름 분리기가 `7_value`로 바꾼 뒤 접두사를 붙였다. 생성자 인자 이름이 달라졌지만 기존 공개 설정 검사에는 숫자 시작 속성이 없어 발견하지 못했다.

처음에는 모델 등록 dict를 합치기만 하면 된다고 예상했다. 진단 복사본에서 같은 ImportError가 남아 이 가정이 반증됐다. 실제 컨텍스트 전달까지 복구한 뒤 공개 core 검사 15/15가 통과했다. 숫자 속성명 수정은 공개 config 검사 15/15가 통과했다. 이 진단 복사본은 실제 새 개발 실행에 전달하지 않았고 이전 후보도 수정하지 않았다. [가설·반증·정정과 진단 영수증](../../benchmark-runs/d095-public-boundaries-20261017-01/diagnosis.md).

## 보강한 검사와 실행 연결

[공개 v5 검사](../../benchmarks/e2e-swe/public-checks/extensions/schema_boundaries.py)는 inline string/object/array 응답으로 생성한 API 모듈과 네 함수의 import·callable 여부를 검사한다. 숫자·밑줄 시작 속성명은 세 종류 접두사로 생성자 → 직렬화 → 역직렬화 왕복을 검사한다. 공개 명세로 별도 fixture를 작성했으며 숨김 fixture나 기대 inline 클래스명은 사용하지 않았다.

[assertion v3](../../benchmarks/e2e-swe/public-checks/assertions.v3.json)의 경로를 [실제 산출물·담당 연결 코드](../../src/orchestration/adaptive-public-owner-evidence.mjs)가 현재 artifact/task owner로 해석한다. 요구사항 담당이 다르다는 이유로 실제 producer 후보를 제외하지 않는다. checker SHA, 실행된 실패 assertion, 산출물 revision, 실제 회차 plan hash와 runtime binding을 확인한다. 없는 담당은 만들지 않으며 후보 연결을 원인 증명으로 취급하지 않는다.

실제 첫 공개 실패에서 산출물 후보 5개·연결 근거 6개가 기록됐다. Jev의 담당 추론과 공개 근거를 합쳐 첫 수리에 작업자 5개, 다음 수리에 2개를 호출했다. Jev 실제 POST **23회** 모두 같은 요청 해시의 initial / before_reservation / before_post 검사 영수증을 남겼다. **69/69개 일치, 누락 0개**다. ## 늘어난 시간·토큰·비용

- 작업자 재호출이 D094의 2회에서 이번 7회로 늘었다. 이번 Claude 작업자 토큰은 초기 개발 389,959개, 수리 1,111,416개다. Jev 판단 토큰은 입력·출력 합계 599,720개다.
- 첫 수리의 `adaptive-leaf-n1`은 136,086토큰을 사용하고 파일 3개를 반환했지만 이전 bytes와 차이가 없었다. 이 변경 없는 재호출 1회는 별도로 보존했다. 해당 호출의 참고 환산 비용은 **추정 $1.170184**다.
- 스키마 모델 수리 작업자에서는 유효한 도구 호출을 만들지 못한 뒤 CLI가 추가 응답을 요청한 기록이 1회 있었다. 해당 프로세스의 입력은 캐시 포함 245,145토큰, 입력 캐시 생성은 244,424토큰이었다. CLI 내부 보정은 Jev 재호출이나 작업자 프로세스 재호출과 구분한다. [CLI 내부 보정 감사](../../benchmark-runs/d095-public-boundaries-runtime-20261017-02/native-tool-corrections.json).
- Jev 판단 콜의 누적 wall time은 **54.317초**, Claude CLI 프로세스 누적 시간은 **44분 34.130초**다. 병렬로 겹친 구간이 있어 이 합계를 전체 실행시간에 더하지 않는다. Jev 수치는 전송 전 검사·장부 처리 등을 포함한 콜백 시간이며, 서버 추론 시간만 분리한 수치는 아니다. Claude 수치도 시작·추론·출력·구조화 반환을 포함한다. [구간별 영수증](../../benchmark-runs/d095-public-boundaries-runtime-20261017-02/component-times.json).

캐시 포함 토큰은 `Jev 입력 + Jev 출력 + Claude 일반 입력 + cache_read + cache_creation + Claude 출력`으로 집계했다. thinking은 출력의 부분집합이므로 다시 더하지 않았다. 이번 Claude 입력 캐시 읽기는 **71,564토큰**, 생성은 **1,098,694토큰**이었다.

비용은 실제 월정액 청구액이 아닌 **참고 환산 추정치**다. Claude는 동결한 공식 Standard 단가 계약으로 **추정 $14.4624843**, Jev는 기존 장부의 과거 입력팩 환산율로 **추정 $0.3432036**, 합계 **추정 $14.8056879**다. 실제 청구액과 구독 배분은 미확인이다. [Claude 단가·사용량 규칙](contracts/claude-pricing.v1.json). Claude CLI 프로세스는 12회이며 내부 HTTP 요청 총수는 확인하지 않았다.

## 숨기지 않고 보존한 첫 실행기 실패

첫 v15 실행은 제가 추가한 결속 검사에서 초기 계획 전체와 회차별 실행 계획이 완전히 같아야 한다고 요구해 정상적인 회차 변경을 거부했다. `PUBLIC_OWNER_ASSERTION_RUNTIME_DRIFT`로 수리 전 종료됐으며 공개 75/93, 독립 58/63, 수리 호출 0회였다. **17분 40.652초 · 643,247토큰 · 추정 $4.1821504**를 별도로 보존했다. 이 실패를 모델의 개발 실패로 분류하지 않았다.

v16은 실제 회차 계획의 해시와 고정된 구현 담당을 별도로 검사한다. 정상적인 회차·검사 장식 변경은 허용하고 담당자 변경, 쓰기 범위 확대, 오래된 계획 해시는 거부한다. 실제 round-0 자료와 이후 회차, 변조 반례를 포함한 관련 **64개 검사 통과·skip 0개** 후 다시 실행했다. 실제 두 수리 회차에서도 이 결속 검사를 통과했다.

두 실제 실행의 활성 실행시간 합은 **51분 57.333초**, 사용량 **2,744,342토큰**, 참고 비용 **추정 $18.9878383**다. 첫 시작 이벤트부터 두 번째 종료 이벤트까지의 벽시계 경과는 **54분 44.217초**이며 중간 실행기 수정·사전 검사 간격을 포함한다. 첫 모델 실행 전의 구현 작업과 메인 대화 토큰은 이 수치에 포함하지 않았다.

과거 동결 계약을 대상으로 하는 통합 검사 11개는 현재 소스의 drift를 거부했다. 이를 과거 계약 재pin으로 덮지 않았고 실패 로그를 보존한 뒤, 새 v16 실제 manifest에 연결한 검사 64개를 실행했다. 정상 대조군 8개·결함 대조군 85개는 검사 장치 검증이며 제품 완료와 구분한다.
