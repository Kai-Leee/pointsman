## 입력 축소가 적용되지 않은 복잡한 실패

모델 선택 조건의 실제 수리 8회는 총 1,645,771B → 동일로 입력 감소가 0B였다. 첫 3회는 현재 패키지 import 오류, 67개 미실행 사례, 담당 불명 3건 때문에 전체 문맥을 유지했다. 다음 5회는 담당 불명과 전체 사례 미실행이 해소됐지만, **현재 `T.integration.diagnostics`의 미도달 assertion 4개** 때문에 전역 보호 규칙이 계속 적용됐다.

정확한 경로는 `/artifact_repair/failure/repair_scope/not_reached_assertions[0]`이다. 현재 공개 검사는 19 assertions까지 진행한 뒤 `warning diagnostic UntypedArray`에서 멈췄다. 공개 checker 427행의 경고 검사가 실패해 443행의 overwrite/hook 검사 4개에 도달하지 못했다. 이전 회차의 같은 사례는 `ModuleNotFoundError`로 11 assertions 후 멈췄으므로 과거 표지의 잔재가 아니다. 원본과 실제 전송본을 8/8 대조했으며 감사 근거 45개 SHA는 불변이다. [현재 실패 경로 감사](../../benchmark-runs/d091-codex-20261016-01/worker-payload-live-routing-fallback-analysis.md).

후속 정책은 검증 미완료와 소스 문맥 부족을 구분해야 한다. 현재 소스·담당·권한·의존 관계가 연결되고 미도달 검사의 관련 범위가 입증될 때만 산출물 단위 투영을 허용하는 안이다. 불명확한 경우 전체 문맥 유지와 공개·독립 재검사를 계속해야 한다. 이 변경과 선행 경고 수리 후 재검사는 이번 실행에 적용하지 않았으며, 효과도 측정하지 않았다.

담당 판단은총13회 중7회 인코더가적용됐다. 모델선택조건은11회 중5회적용,780550→707867B로72683B 감소했다. 첫raw-v1 6회는UNSUPPORTED_OWNER_SCHEMA로 명시적보존돼0B, 이후projected-v2 5회는감소했다. `repair-budget-v3`가인코더이전에 분할개수를결정해바이트가줄어도이미정한POST수는줄지않았다. [완료응답22개 고정스냅샷의원인분석](../../benchmark-runs/d091-codex-20261016-01/owner-payload-live-routing-analysis.md)은첫6raw와그다음완료4/예정5v2를구분하며최종11호출합계와혼용하지않는다.

다음개선은raw-v1 lossless지원과분할전인코딩, 실제모듈/인터페이스검증을반영한모델프로필, no-op후담당/새근거확인이다. 모두제안이며이번에구현하거나추가유료실행하지않았다. 저렴한단가만으로전체완료비용최적화를보장할수없고, 현재모델선택질문은공식역량/가격설명을이용할뿐과제유형별성공률이보정되지않았다. 기본run/pair의작업자모델은고정이고새모델선택은v8/adaptive실험경로에서만명시사용한다.

## D090에서 왜 수리 입력이 컸는가

D090의 Jev 실행은 초기 개발 뒤 공개92/93에서 선택적 필드의 UNSET 처리를 수리했고, 공개93/93·독립63/63으로 완료했다. 당시 수리 작업자 한 호출은 입력67,721·출력6,587로 총74,308토큰이었다. 입력 JSON은211,268바이트이며 `available_files`가175,885바이트로175885/211268=83.25%를 차지했다. 실패 근거는26,044바이트였다. [원문 필드 감사](../../benchmark-runs/d091-codex-20261016-01/worker-payload-audit-final.json).

0바이트 투영의 원인은 전체 문맥 fallback이 발동했기 때문이다. 정규식이 생성할 코드의 문자열 속 `__import__`까지 실행 중 동적 import로 보았고, 읽기 전용 패키징 메타데이터의 console entrypoint·일반적인 generate 인터페이스 문구가 CLI→generator→metadata→전체 템플릿으로 읽기 범위를 넓혔다. 실제 `get_template(template)`은 동적이지만 검증된 PackageLoader/FileSystemLoader의 후보 템플릿 묶음으로 경계를 만들 수 있었다.

새 `artifact-family-closed-v2`는 Python AST를 후보 실행 없이 분석해 문자열과 실제 호출을 구분하고, 선택한 산출물과 검증된 의존 파일·필요한 템플릿 가족을 남긴다. 알 수 없는 실제 동적 import/외부 로더/구문 오류/불완전 근거는 전체 입력 fallback을 유지한다. 요구사항·실패 원문·권한·출력 계약은 제거하지 않는다. [정책](contracts/codex-worker-input-projection.v2.json) · [구현](../../src/benchmark/codex-worker-input-projection-v2.mjs).

같은 D090 수리 입력을 오프라인 재현한 결과211,268→146,734바이트,64,534/211,268=30.5460% 감소했다. 전체 파일 본문38→17개이며21개/62,736본문 바이트를 제외했다. 실패 원문26,044바이트와 모든 비파일 필드는 동일했다. 이는 같은 요청의 바이트 측정이며 새 실제 토큰·시간·품질 측정이 아니다.

Jev의 실패 담당 질문도 전체 원문을 여러 필드로 반복하지 않게 인라인 열/행과 고정 키 목록으로 표현한다. 원본 질문59,403→53,299바이트,6,104/59,403=10.2756% 감소했다. 전송된 wire만으로 원래 JSON 바이트를 복원해 일치하는지 검사했다. 외부 경로·해시를 Jev가 원문처럼 읽는다는 가정은 없다. 실패·요구·담당 후보/권한·unknown은 원문을 유지한다. ## 모델 선택이 실행에 연결되는 방식

[질문 정본](contracts/codex-worker-profiles.v1.json).

## 실행과 결과의 경계

각 조건은 새 분해 판단과 새 산출물을 생성한다. Jev 고정 모델/모델 선택 조건도 동일 DAG를 재생하는 비교가 아니므로 계획·작업자 수·발생 실패가 달라질 수 있다. 단일 실행의 관찰 차이를 모델 선택만의 인과 효과로 확정하지 않는다.

각 조건은 동일 OpenAPI client generator 과제/catalog·공개93/독립63·동시 작업자2/최대30·수리2회다. 앱 내장CLI0.162.0-alpha.17.2와 같은 frozen 환경/소스에서 한 번씩 순차 실행한다. Jev 모델 선택 조건만 작업자 프로필을 바꾼다. 숨김 검사 내용은 계획·질문·수리에 넣지 않는다. 원래 공유 장부를 유지하고 불확실 결과를 자동 재실행하지 않는다.

[첫 결과](../../benchmark-runs/d091-codex-20261016-01/root-focused-tests-01.tap) · [추가 검증](../../benchmark-runs/d091-codex-20261016-01/root-additional-focused-tests.tap) · [계측 정정](../../benchmark-runs/d091-codex-20261016-01/test-selection-correction.json).
