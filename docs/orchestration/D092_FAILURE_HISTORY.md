# D092 — 과거 공개 실패·해결 이력과 반복 비용

2026-10-17 KST. 사람을 위한 분석 문서다. 모델 선택 입력은 별도 공개 성과 집계기를 사용한다. 이 문서에 나오는 독립 채점 **집계**는 사람의 제품 완료 판단을 위한 역사 기록이며 모델·담당 질문에 전달하지 않는다. 숨김 검사 본문·실패 상세를 읽지 않았다. 모델·계정·GET·Docker·원장 호출과 테스트 재실행은 하지 않았다.

현재 확인된 문제는 초기 판단의 지연만이 아니다. 잘못되거나 불완전한 초기 구현이 담당 판단, 모델 재선택, 넓은 수리 입력과 재호출을 늘린다. D090에서는 두 제품이 모두 완료됐고 Jev가 전체 시간을 줄였다. D091에서는 초기 판단은 여전히 빨랐지만 모델 선택 조건이 수리 8회까지 확대됐으며 제품 완료에 도달하지 못했다. 이 이력은 모델·노력도 선택에 **실제 공개 결과와 재수리 비용**을 함께 넣어야 한다는 근거다. 어떤 새 선택 정책의 개선 효과를 입증한 것은 아니다.

### A01 누락의 정확한 해석

`codex-e2e-mac-20261014-02/jev-arm-audit.json`과 그 안의 원본 4개 SHA가 현재 바이트와 모두 일치했다. 실패 작업자의 출력은 staged 상태였고 미실행 작업에는 출력 자체가 없었다. 전체 22개 산출물을 순회하는 완성 후보 validator가 `failure.artifact_revisions.A01`을 먼저 요구해 `ADAPTIVE_INFERRED_ARTIFACT_BINDING`으로 끝났다. 이어지는 전체 키 동등 조건도 실패했겠지만 실제로는 그 조건에 도달하지 않았다.

A01이 생성 코드의 원인 담당이라는 뜻이 아니다. revision을 꾸며 넣거나 완성 후보 검증을 약화하는 대신, 확정 revision·실패 stage·미실행 항목을 각각 검증하는 별도 상태 계약이 필요했다. 이미 성공한 작업을 다시 부르지 않고 아직 수행하지 않은 작업을 계속하는 것이 이 보강의 목적이다. 이후 다른 실행에서 막힘이 사라졌다는 사실과 해당 분기 실제 발동·수리 성공은 다른 관측이다.

### enum·기본값 실패는 소비자 한 곳만 고치면 재발할 수 있다

D076 확장 읽기 사례는 A10의 `build_enum` 자체 결함을 찾는 데 필요 문맥이 있었다. D089는 참조 이름을 잃은 A13 producer 뒤에서 A12 기본값 소비자를 수리하는 문제가 있었다. D091 routed 최종 실패에는 `T.R14.01–04`, `T.integration.defaults`, `T.R11.05` 등이 다시 남았다. 같은 공개 요구 계열의 재발이지, 생성 소스가 다른 실행에서 같은 root cause가 반복됐다고 증명된 것은 아니다.

다음 담당 입력은 공개 assertion 기대값·실제값·원래 참조와 해당 IR/producer/renderer 전달 관계를 묶어야 한다. 소비자 메시지에 나타난 파일만 바로 원인 담당으로 간주하면 upstream 정체성 손실을 놓칠 수 있다. 관계가 미확정이면 후보 가설과 확정 담당을 구분한다.

## 최신 adaptive의 full context와 no-op는 실제 현재 증거다

원본 `cohort/jev-model-routing/adaptive-execution/result.json`의 공개 round와 작업자 입력을 함께 대조했다.

1. round0에서 5개 suite가 생성 패키지를 import하지 못했다. 공개 사례 67/93개가 미실행으로 남았고 unresolved owner 3개가 있었다. 다음 수리 3개의 합 472,681B는 `incomplete_failure_or_owner_evidence`, `unresolved_or_unexecuted_evidence`, `incomplete_public_evidence`로 전체 문맥을 보존했다.
2. round1에는 이 5개 suite의 import 오류와 unknown owner가 해소됐다. 그러나 현재 `T.integration.diagnostics`는 `AssertionError: warning diagnostic UntypedArray`에서 멈췄고 뒤의 assertion 4개가 `not_reached`였다. 이는 과거 오류가 잘못 복사된 값이 아니다. 같은 case의 관측 assertion 수가 11에서 19로 바뀌고 오류 유형도 ModuleNotFoundError에서 AssertionError로 바뀐 현재 원문과 일치한다.
3. 다음 수리 5개는 모두 `/artifact_repair/failure/repair_scope/not_reached_assertions[0]`에 의해 `unresolved_or_unexecuted_evidence` 전역 guard가 적용됐다. 합 1,173,090B가 그대로 전달됐다. 관련 없는 작업자까지도 현재의 미검사 assertion 때문에 모두 38개 본문을 받았다.
4. 총 8수리 모두 full fallback, 1,645,771→1,645,771B, 감축 0B다. 문맥 안전을 위해 남긴 동작이지만, 검증 미완료와 소스 문맥 불충분을 구분하지 않는 보수성이 있다. guard를 삭제하거나 not_reached를 passed로 바꾸는 것은 해결이 아니다.
5. 그중 2회는 반환 accepted 파일 전부가 같은 호출의 원문 SHA와 같았다. 첫 no-op 2파일·56,558토큰, 다음 4파일·83,852토큰, 합 **140,410토큰/수리 8회 중 2회**다. provider 시간 합 85.124초와 짧은 문맥 참고액 $0.3117이며, 병렬 임계 경로에서 그만큼 절약 가능하다는 뜻은 아니다.

[상세 공개 경로 분석](../../benchmark-runs/d091-codex-20261016-01/worker-payload-live-routing-fallback-analysis.md)의 8개 worker JSON 경로·현재 public 오류·38개 본문 유지 원인을 보존한다. D092 감사는 두 no-op의 파일 SHA를 다시 확인했다. no-op 자체가 기능 실패를 증명하는 것은 아니지만, 요구가 여전히 실패한 상태의 같은 출력 재호출은 새 근거 없이 반복해서는 안 된다.

## 다음 재발 방지 규칙 — 제안이며 이 문서에서 미구현

1. **과거 성과의 분모를 고정한다.** task/phase·요청 model/effort·현재 source/환경 revision과 공개 검사 binding이 모두 있을 때만 success/failure로 집계한다. 미실행은 unknown, 수리 전후가 다른 소스이면 같은 시도 성공률로 합치지 않는다. 표본0은0%가 아니다. 독립 결과는 선택 입력에 넣지 않는다.
2. **부분 후보를 완성 후보로 검사하지 않는다.** staged 실패 출력 SHA, 확정 revision, 미실행 산출물을 분리 검증한다. 실패 코드 자체가 담당을 이미 결정하는 경우 추가 owner 추론 대신 해당 bounded repair를 선택할 수 있지만 기존 권한·source/readiness 검증은 유지한다.
3. **같은 공개 실패의 producer 경로를 전달한다.** assertion 기대·실제값과 참조/IR/renderer 연결을 보존한다. 소비자 파일만 배정하지 말고 공개 source-bound 후보가 producer를 포함하는지 확인한다. 원인 가설을 확정 사실로 승격하지 않는다.
4. **no-op 후에는 새 근거를 요구한다.** 동일 실패·같은 쓰기 소스·동일 dependency revision·같은 읽기 증거에 대한 재호출이면 모델/effort만 바꾸지 말고 담당·원인·필수 읽기/쓰기 범위가 달라졌는지 확인한다. 파일을 바꾸지 않아도 다른 현재 검사가 통과했다면 no-op이라는 이유만으로 실패 처리하지 않는다.
5. **미검사 assertion과 문맥 증명은 별도로 관리한다.** not_reached4를 보존하고 다음 검사를 계속 요구하되, 그4개가 특정 CLI 경로에 묶이고 다른 작업자의 의존 closure가 충분히 증명되면 그 작업자까지 full38을 강제할지 별도 판정한다. 애매한 동적 import·템플릿·owner 근거는 fallback을 유지한다. guard 삭제나 assertion 생략은 금지한다.
6. **분할 전에 손실 없는 입력 형태를 평가한다.** raw-v1도 지원한 다음 인코딩된 요청을 예산 분할 전에 계측하는 새 정책을 검토한다. 질문/실패/권한/공개 불확실성 round-trip을 유지한다. 기존 raw 실패를 조용히 통과시키지 않는다.
7. **모델 registry를 한 정본에서 검증한다.** destination·정산·input admission·returned model alias의 교집합을 호출 전 확인한다. 미검증 alias는 모델 실패로 학습하지 않고 integration/unknown으로 기록한다. 공식 본문 한도와 내부 토큰 목표를 구분한다.
8. **모델·effort는 단가보다 완료 경로 기대비용으로 비교한다.** 초기 호출 비용뿐 아니라 공개 성공/재수리/no-op, owner/profile 호출, full-context 비율, 병렬 dependency 경로를 포함한다. 다음 비교는 같은 공개 완료 기준을 충족한 제품의 wall·token·참고액을 우선하고 실패 종료시간 절감은 별도 표시한다.

실행 규칙을 구현·검증한 상태와 이 문서의 제안을 혼합하지 않는다. 이번 작업은 과거 근거 정리와 새 오프라인 감사뿐이며 새 모델 선택 정책의 완료율·시간·비용 효과는 아직 측정하지 않았다.
