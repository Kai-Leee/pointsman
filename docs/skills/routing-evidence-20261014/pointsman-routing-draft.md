# Pointsman routing

This is a repository-owned operational draft. A general skill registry, doctor and skill dispatcher are not yet implemented. Do not invent their commands or claim installation makes routing automatic. Read [the routing contract](references/routing-contract.md) before using this draft.

Resolve the Pointsman source root separately from the target project root. Pin the release/research revision and current run manifest; read the latest STATE and applicable instructions. Older dated sections and old installed copies are not the current execution contract.

## Establish the decision

Honor the user's explicit workflow or model choice. Identify the declared event, desired outcome, requirement IDs, public checks and current artifact revision. Reuse the registered English question and candidate criteria; fill only the allowed variables. Prepare missing novel workflow definitions once, outside the repeated decision loop.

Filter candidates by supported tools, required inputs, allowed scope and current availability before semantic selection. A sole candidate can bypass inference only when its applicability is already established. With no applicable candidate, report the missing prerequisite or unsupported route and let the main agent resolve it. With multiple eligible candidates, send sufficient inline evidence through a supported, validated Jev path.

Keep skill selection and model/effort selection distinct. Send concise workflow criteria rather than every skill's full text. Read the selected skill's body and relevant references only after selection. Local paths and hashes do not give Jev access to omitted source material.

## Apply and check

Resolve a valid answer through a registered ID-to-handler binding. Check the answer envelope, allowed candidates, evidence revision, dependencies and write scope. Never execute a model-generated shell command or grant permissions because a model selected a label. Do not ask the main model to repeat a valid comparison; it still implements and verifies the chosen work.

Record decision ID, contract/evidence revisions, candidate exclusions, actual selected ID, executed handler/worker receipt and public check outcome. Treat a selected skill, a dispatched worker and a passing product check as separate events. Missing usage/cost is unknown; distinguish monthly billing from token-price estimates.

For public-check failures, retain assertion/expected/actual evidence, current ownership and relevant prior attempts. Use the selected runtime's owner/scope/recovery policy. Do not use hidden grader contents as repair input. Unknown POST outcomes require reconciliation, not an automatic retry. A new attempt ID alone is not new failure evidence.

## Current boundaries

The D083 research path has specialized decomposition, profile selection and repair ownership. It does not supply a universal skill router. The public main MCP exposes decision tools but does not force every native tool call through the repository validator. If a required gateway or handler is unavailable, report that specific gap rather than silently using an unvalidated substitute.

Jev secrets remain in the server runtime. `~/workspace/.env` is the local default; deployment uses runtime secrets. Verify destination and authenticated model listing separately from inference. This draft changes neither authorization nor the active experiment's cloud-only ledger, sequential execution and stopped-run rules.
